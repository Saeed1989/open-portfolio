One form system, thirteen sections, and the places where publish bites

Everything below renders through the field components on the field states reference — eleven types, one invalid treatment, one focus ring. Section editors here are cropped to the content pane; hub screens carry the full shell. Tenant is Dana Villalobos, a staff backend engineer, at dvillalobos.openfolio.site.

Judgement calls I made

  • Project modal: single scroll with a sticky section nav, not tabs. Tabs would hide half the publish-blocking fields behind a click, and since publish reports every failure at once, a tab would need an error badge that reproduces the error list anyway. The nav carries per-group gap counts and a publish error deep-links straight to the field.
  • Section state is a pill, not a colour on the toggle. “Enabled but empty” is not a weaker kind of on, so it reads as its own word with the consequence spelled out.
  • Save never validates content. Required-but-empty is a grey dotted marker during editing; it only turns red after a publish attempt. Otherwise a half-written draft is a wall of errors.

Where a product rule forces a layout I would push back on

  • “Enabled but empty” is a state the tenant should not have to hold. It exists because enable and content are separate, and the manager has to explain it three ways. Deriving visibility from content and dropping the toggle would remove the state entirely; I have shown the rule as written, but it is the one I would change.
  • Impact cannot be saved empty is the only content rule enforced at save, which contradicts the save/publish split everywhere else. I kept it and marked it explicitly in the UI, because one inconsistent gate is a support ticket.
  • A sixth project refused outright at save needs the refusal to arrive before authoring, not after — so the cap sits on the Add button, not in a post-hoc error.

Judgement call — single scroll with a sticky section nav. Rejected: Card / Case study tabs. Two reasons. Publish reports all failures at once, so a tab would need an error badge that duplicates the error list, and the tenant would still have to click to see which field. Business case

*required to publish418 / 1200
Six controls. Everything else is stripped on paste.

Analytics had become the constraint on shipping. Every product team needed warehouse data to measure a release, and the platform team of four was the only route in — we were reviewing twelve ingestion PRs a week and still missing the forty-minute freshness target that the pricing team depended on.

Two failures compounded:

  • Every source was a hand-written DAG, so a schema change in one upstream table broke jobs nobody owned.
  • Backfills were a ticket to us, which meant analysts copied tables into spreadsheets instead of waiting. 

The business cost was not the latency. It was that nobody trusted a number enough to act on it the same day.

AutosavedShape only — a half-written body saves. Length and presence are checked at publish.

Finding to settle: the brief asks for six controls but names five — bold, italic, underline, bulleted, numbered. I drew those five plus clear formatting, the only sixth that adds no capability. If the intended sixth was something else (blockquote, code, undo), say which and it is one registry flag.
